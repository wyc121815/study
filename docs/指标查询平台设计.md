# 指标查询平台设计方案

> 状态：设计稿（P0 的 SQL 执行内核已落地）
> 定位：在现有「数据库连接管理平台」之上，把"能连库"升级为"能取数、能看指标"。

## 1. 目标与非目标

**目标**

- 让业务/运营同学不写 SQL 也能取到口径统一的指标，比如「昨日各渠道支付成功率」。
- 指标口径集中定义、只维护一处，避免同一个人把同一份数算成三个版本。
- 所有查询只读、可审计、有配额，连接密码依然不进业务同学视野。
- 查询结果可直接渲染成单值 / 趋势 / 表格，而不是返回一堆原始行。

**非目标（当前阶段）**

- 不做可视化大屏编排、不做指标体系治理平台、不做数据血缘。
- 不做实时流式计算，取的是库里的存量数据。
- 不替代 BI 工具，定位是"轻量、口径固定、即查即看"。

## 2. 现状与可复用资产

已经具备的、指标平台可以直接吃的能力：

| 资产 | 位置 | 指标平台里怎么用 |
| --- | --- | --- |
| 连接配置与 AES-GCM 凭据 | `conn-service` · `db_connection` | 作为指标的数据源，无需重复登记 |
| 多数据库方言抽象 | `conn-service` · `DbType` | 拼 JDBC URL、挑驱动、生成方言 SQL |
| SQL 执行内核（新） | `POST /api/queries/execute` | 指标查询的取数底座 |
| 只读 / 行数 / 超时护栏 | `SqlStatementGuard` + `app.query.*` | 指标查询原样复用 |
| 统一鉴权与身份透传 | 网关 + `@RequireRole` + `X-User-Id` | 指标级权限与审计里的操作人来源 |
| 统一返回体 / 异常 | `Result` / `ErrorCode` | 指标接口沿用同一套契约 |

结论：**不重起炉灶**，在 `conn-service` 内先长出指标这一层，体量大了再拆服务。

## 3. 核心概念模型

```
数据源(datasource) ─── 复用 db_connection
      │
      └── 指标(metric) ── 一份带参数与输出契约的查询定义
                │
                ├── 参数(parameter)   时间范围 / 枚举 / 自由文本
                ├── 维度(dimension)   group by 列，如渠道、地区
                ├── 度量(measure)     指标值列，如成功率、GMV
                └── 输出契约(contract) 决定能渲染成什么图
```

| 概念 | 说明 | 例子 |
| --- | --- | --- |
| 数据源 | 指向已保存连接，可限定用哪个库/账号 | `prod-mysql-order` |
| 指标 | 一个有唯一编码、有口径说明的可执行查询 | `pay_success_rate` 支付成功率 |
| 参数 | 查询时由用户或系统填入的绑定变量 | `startDate`、`endDate`、`channel` |
| 维度 | 结果里用于分组/下钻的列 | `channel`、`region` |
| 度量 | 结果里的数值列及其单位、格式 | `success_rate`（百分比，2 位小数） |
| 输出契约 | 声明时间列 / 维度列 / 度量列，决定渲染方式 | 时间序列 → 折线图 |

## 4. 分层架构

```
前端
 ├─ 指标目录页（查找 / 收藏 / 最近）
 ├─ 指标详情页（参数区 + 图表 + 明细）
 └─ 指标编辑器（管理员：SQL + 列角色标注 + 预览）
        │
API 层  /api/metrics/**（查询）/api/metric-definitions/**（定义，仅 ADMIN）
        │
指标语义层
 ├─ 参数绑定与 SQL 渲染（命名参数 → 预编译占位符）
 ├─ 输出契约校验（时间/维度/度量列必须存在于结果中）
 ├─ 时间粒度改写（day/hour/month 白名单 → 方言函数）
 └─ 渲染形态推断（single_value / time_series / table）
        │
查询执行层（复用本次实现的 SQL 内核）
 └─ 连接解析 → 解密凭据 → 只读校验 → 执行 → 行数/超时护栏 → 结果标准化
        │
数据层：platform_conn（连接、指标定义、查询日志）+ 目标库（只读）
```

## 5. 指标定义：SQL 模板 + 输出契约

### 5.1 两条路线怎么选

| 路线 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| A. SQL 模板 + 声明式契约 | 指标是一段带命名参数的 SQL，外加"哪列是时间/维度/度量"的元数据 | 落地快，能覆盖任意复杂查询 | 口径靠模板作者自觉 |
| B. 语义层（度量 + 聚合 + 维度） | 平台按结构化描述生成 SQL | 口径强一致，可自动下钻 | 实现重，复杂 SQL 表达不了 |

**建议：先 A，为 B 留口子。** 契约层已经声明了时间/维度/度量，等 B 需要时，
这些元数据就是语义层的输入，不用推翻重来。

### 5.2 指标定义示例

```json
{
  "code": "pay_success_rate",
  "name": "支付成功率",
  "description": "成功支付笔数 / 支付总笔数，按渠道和日期分组",
  "datasourceId": 12,
  "sql": "SELECT DATE(pay_time) AS stat_date, channel, COUNT(*) AS total_cnt, SUM(IF(status = 'SUCCESS', 1, 0)) AS success_cnt FROM pay_order WHERE pay_time >= :startDate AND pay_time < :endDate AND (:channel IS NULL OR channel = :channel) GROUP BY DATE(pay_time), channel",
  "parameters": [
    { "name": "startDate", "type": "DATE", "required": true, "default": "today-7d" },
    { "name": "endDate", "type": "DATE", "required": true, "default": "today" },
    { "name": "channel", "type": "ENUM", "required": false, "options": ["WECHAT", "ALIPAY", "CARD"] }
  ],
  "contract": {
    "timeColumn": "stat_date",
    "dimensions": [{ "column": "channel", "label": "渠道" }],
    "measures": [
      { "column": "success_cnt", "label": "成功笔数", "unit": "笔", "format": "integer" },
      { "column": "total_cnt", "label": "总笔数", "unit": "笔", "format": "integer" }
    ],
    "render": "time_series",
    "owner": "data-team",
    "tags": ["支付", "核心"],
    "cacheSeconds": 300
  }
}
```

要点：

- **命名参数 `:name`**：查询前统一改写成 JDBC 的 `?` 并 `setXxx` 绑定，模板字符串永不直接拼接用户输入。
- **输出契约与 SQL 解耦**：SQL 改列名时契约同步改，加载/保存时校验列存在，避免上线后图表空转。
- **时间粒度**：`granularity`（hour/day/week/month）只做白名单映射，不同方言各自生成
  `DATE_FORMAT(...)` / `date_trunc(...)`，不接受用户自定义表达式。

### 5.3 渲染形态推断

| 契约特征 | 渲染 | 例子 |
| --- | --- | --- |
| 无维度、无时间列 | 单值卡片（可带同环比） | 今日支付成功率 |
| 有时间列 + 度量 | 折线/柱状趋势图 | 近 30 天成功率趋势 |
| 有维度 + 度量 | 分组柱状图 + 明细表 | 各渠道成功率对比 |
| 任意 | 明细表兜底 | 原始结果总能看到 |

## 6. 查询执行流程

```
用户点「查询」
  → 校验参数（类型、必填、枚举白名单、时间范围上限）
  → 取指标定义，确认当前用户对指标 + 数据源有权限
  → 渲染 SQL：命名参数 → 占位符；粒度 → 方言函数；强制追加行级权限过滤
  → 命中缓存？命中直接返回
  → 复用 SqlQueryService：只读护栏 + 行数上限 + 超时 + 结果标准化
  → 结果按契约切分时间/维度/度量，补单位与格式化
  → 写查询日志（指标、参数、行数、耗时、操作人、是否命中缓存）
  → 返回给前端渲染
```

缓存键建议：`metricCode + 归一化参数 + 数据源版本`，TTL 取指标上的 `cacheSeconds`。
新增/修改指标定义时按指标维度失效，避免"改了口径还看旧数"。

## 7. API 设计（草案）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/metrics` | 指标目录，支持 `keyword` / `tag` / `datasourceId` / 分页 |
| GET | `/api/metrics/{code}` | 指标详情：参数定义 + 契约 + 口径说明 |
| POST | `/api/metrics/{code}/query` | 执行指标查询，返回按契约切分好的结果 |
| POST | `/api/metrics/{code}/preview` | 编辑器内试跑，可传临时 SQL 与参数 |
| GET | `/api/metrics/{code}/history` | 最近查询记录（可见范围取决于权限） |
| GET/POST/PUT/DELETE | `/api/metric-definitions/**` | 指标定义维护，仅 ADMIN |
| GET | `/api/metrics/{code}/export` | 导出 CSV（复用同一份结果，行数上限一致） |

统一的查询请求体：

```json
{
  "params": { "startDate": "2026-09-01", "endDate": "2026-10-01", "channel": "WECHAT" },
  "granularity": "day",
  "dimensions": ["channel"],
  "maxRows": 1000,
  "noCache": false
}
```

返回体在通用 `SqlQueryResult` 之上加一层指标语义：

```json
{
  "code": 0,
  "data": {
    "metricCode": "pay_success_rate",
    "render": "time_series",
    "columns": [{ "key": "stat_date", "role": "time" }, { "key": "channel", "role": "dimension" }],
    "rows": [["2026-09-01", "WECHAT", 128, 120]],
    "measures": [{ "key": "success_cnt", "unit": "笔", "format": "integer" }],
    "rowCount": 1,
    "elapsedMillis": 42,
    "cached": false
  }
}
```

## 8. 前端交互

- **指标目录**：卡片/列表，按标签分组，支持搜索与收藏；卡片上直接显示口径一句话与更新人。
- **指标详情**：顶部参数区（时间范围选择器 + 维度筛选下拉），中部图表，下部明细表与导出。
  参数变化即重查，查询中显示骨架屏；空结果给"调整时间范围"的引导。
- **指标编辑器（ADMIN）**：左侧 SQL 编辑器，右侧"列角色"面板（在预览结果表头上点选
  时间/维度/度量并填单位）；点预览即用当前定义试跑，保存前做契约校验。
- **SQL 查询页（已完成）** 保留为"探索模式"：先用它调通 SQL，再一键"存为指标"，
  把探索结果沉淀成定义，避免重复劳动。

## 9. 权限与安全

| 关注点 | 做法 |
| --- | --- |
| 只读 | 复用 SQL 内核的只读护栏；数据源账号仍建议只给 `SELECT` |
| 注入 | 参数一律走预编译绑定；粒度/表名等无法绑定的部分走白名单枚举 |
| 指标权限 | 指标可标 `visibleRoles` / 可见用户组，目录与查询都按此过滤 |
| 数据源权限 | 指标只能挂在用户有权使用的连接上；无权连接不出现在选择器 |
| 行级权限 | 渲染 SQL 时强制注入过滤（如 `AND region IN (:allowedRegions)`），模板作者不可绕过 |
| 配额 | 按用户/指标限流（次数 + 并发），防止把指标页当压测工具 |
| 审计 | 每次查询落 `metric_query_log`：操作人、指标、参数、行数、耗时、命中缓存；定义变更另记 |
| 耗时 | 单条查询超时、行数上限与 SQL 查询页共用同一组 `app.query.*` 配置 |

## 10. 数据模型草案

```sql
-- 指标定义
CREATE TABLE metric_definition (
  id            BIGINT       NOT NULL AUTO_INCREMENT,
  code          VARCHAR(64)  NOT NULL COMMENT '指标唯一编码',
  name          VARCHAR(128) NOT NULL,
  description   VARCHAR(512) NULL,
  datasource_id BIGINT       NOT NULL COMMENT '指向 db_connection.id',
  sql_text      TEXT         NOT NULL COMMENT '带命名参数的 SQL 模板',
  parameters    JSON         NULL COMMENT '参数定义',
  contract      JSON         NOT NULL COMMENT '时间/维度/度量/渲染契约',
  cache_seconds INT          NOT NULL DEFAULT 300,
  status        VARCHAR(16)  NOT NULL DEFAULT 'ENABLED',
  owner         VARCHAR(64)  NULL,
  created_by    BIGINT       NULL,
  created_at    DATETIME(3)  NOT NULL,
  updated_at    DATETIME(3)  NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_metric_definition_code (code),
  KEY idx_metric_definition_datasource (datasource_id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT '指标定义';

-- 指标查询日志（审计 + 热度统计）
CREATE TABLE metric_query_log (
  id           BIGINT       NOT NULL AUTO_INCREMENT,
  metric_code  VARCHAR(64)  NOT NULL,
  user_id      BIGINT       NULL,
  params       JSON         NULL,
  row_count    INT          NULL,
  elapsed_ms   BIGINT       NULL,
  cached       TINYINT(1)   NOT NULL DEFAULT 0,
  success      TINYINT(1)   NOT NULL,
  message      VARCHAR(512) NULL,
  created_at   DATETIME(3)  NOT NULL,
  PRIMARY KEY (id),
  KEY idx_metric_query_log_code_time (metric_code, created_at)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT '指标查询日志';
```

缓存走已有的 Redis，不额外建表；`platform_conn` 里加这两张表即可，
和 `db_connection` 同库，避免跨库连表。

## 12. 何时拆成独立服务

当前把指标放在 `conn-service` 里，好处是凭据、方言、执行内核都在手边，改动最小。
出现下列任一信号时再拆出 `metric-service`：

- 指标查询的 QPS / 资源占用开始影响连接管理接口；
- 指标定义与治理逻辑膨胀到需要独立团队维护；
- 需要独立的扩缩容和独立发布节奏。

拆分时凭据有两种走法，需要提前定：

1. **共享 crypto key + 内部接口**：新增仅内网可达（不进网关路由）的
   `GET /internal/connections/{id}/credential` 给指标服务取明文；
2. **凭据下沉**：把连接凭据迁到独立的凭据服务，两边都通过它取数。

无论哪种，都要保证凭据接口**不在网关路由里**，外部拿不到；服务间调用继续带
`X-Internal-Token` 校验。这是本次先在 `conn-service` 内实现、而非直接新建服务的
主要原因——避免过早引入一个需要解密的跨服务调用。

## 13. 待确认问题

1. 指标口径的审批流：谁有权新建/修改指标，是否需要二次确认？
2. 数据源是否要区分"仅供指标使用"的连接，与人工查询用的连接隔离权限？
3. 结果导出的行数上限与脱敏规则（明细里可能含手机号、身份证之类字段）。
4. 是否需要把指标结果回写到平台库做快照，用于"历史口径不漂移"。
